1. Overview

AgentGate governance is a deterministic, rule-based pipeline that runs on every pull request sync. It inspects changed file paths, inferred agent metadata, and (when available) CI status to produce a risk score, test-gap assessment, rule violations, and approval requirement — all without calling an LLM.

The pipeline has four core modules:

  1. Risk scoring — lib/risk.ts aggregates weighted signals from path patterns and PR metadata.
  2. Test gap detection — lib/test-gap.ts flags source changes without accompanying test files.
  3. Rules engine — lib/rules.ts evaluates org/repo rules against the PR context.
  4. Approvals — lib/approvals.ts + lib/collaboration.ts map human decisions to status and audit events.
Deterministic only — AI is separate Risk, test gap, and rule evaluation use regex heuristics and thresholds only. After sync, enqueueAiReviewJob may queue an optional LLM review (AI review architecture); that layer is advisory and does not feed back into risk scores or rule matching.

Orchestration lives in lib/github-sync.ts inside syncGitHubPullRequestRecord. Results are persisted to PostgreSQL via Prisma and surfaced in the dashboard, approvals queue, and (on eligible plans) GitHub check runs.

3. Risk Scoring (lib/risk.ts)

calculateRisk builds an array of RiskSignal objects, each with a fixed point contribution. The total score is the sum of signal scores, capped at 100. The aggregate level comes from mapRiskLevel(score).

3.1 Level thresholds

Score rangeRiskLevel
≥ 75critical
≥ 50high
≥ 25medium
< 25low

Each individual signal also gets its own level via the same mapRiskLevel helper applied to its score.

3.2 Path pattern categories

Signals are triggered when changed file paths match exported patterns in riskPatterns:

Pattern keyMatches (examples)Signal keyPoints

4. Test Gap Detection (lib/test-gap.ts)

detectTestGap compares changed source files (TypeScript, JavaScript, Go, Ruby, Python, Java, C# — excluding test paths) against whether any test files appear in the same diff via hasTestFiles.

4.1 Status outcomes

StatusWhen
none No qualifying source files changed, or test files are present in the diff
warning Source files changed without tests, but none are high-impact paths
high Source files changed without tests, and at least one high-impact file matched

4.2 High-impact file detection

A changed source file is high-impact when its path matches any of:

  • riskPatterns.auth, billing, migration, or api
  • BUSINESS_PATTERN — services/, lib/, domain/, modules/, use-cases/

PR titles matching /\b(fix|bug|regression|hotfix)\b/i increase suggestion confidence and add a regression-test recommendation, but do not alone change status from warning to high.

4.3 Suggestions

For gaps, the function returns up to five suggested test file paths and contextual test cases:

  • API routes → tests/integration/api-routes.test.ts
  • UI paths (components/, app/**/page.tsx) → tests/components/…
  • Other sources → sibling .test.ts under tests/lib/

Additional case strings are appended for bug-fix titles, API changes, and UI file changes. Confidence is high when high-impact files or bug-fix titles are present; otherwise medium.

5. Rules Engine (lib/rules.ts)

evaluateRepoRules(rules, pr) filters enabled RepoRule rows, applies scope constraints, then checks trigger conditions. Each match produces an in-memory RuleViolation (persisted separately during sync).

5.2 Scope filters (matchesScope)

All configured scopes on a rule must pass before the trigger is evaluated:

Scope fieldBehavior
branchPattern Comma-separated substrings or * globs matched against head branch name

labelPattern Must match at least one PR label (labels are empty during default GitHub sync)

minimumRiskLevel PR risk rank must meet or exceed rule minimum (low < medium < high < critical)

6. Approvals

6.1 When approval is required

In syncGitHubPullRequestRecord, requiresApproval is true when any of:

  • A matched rule has action require_approval, request_security_review, request_tests, or block_merge
  • risk.score >= 50 (high or critical level)
  • aiAssisted === true

6.2 Approval state transitions (getNextApprovalState)

ConditionapprovalStatusreviewDueAt
Same headSha and existing status is approved, rejected, or risk_accepted Preserved Preserved if pending logic applies
requiresApproval and no preserved decision pending Existing due date or defaultReviewDueAt(riskLevel)
Not required not_required null

New commits (different headSha) reset approval to pending when approval is still required, unless the PR no longer meets requiresApproval.

6.4 Decision mapping (lib/approvals.ts)

Human reviewers submit one of four decisions via recordApprovalDecision:

Recording creates an Approval row, updates PullRequest.approvalStatus, writes an AuditEvent, and (on eligible plans) posts a GitHub comment and refreshes the check run. Approval workflows require the Team plan (isFeatureAvailable(..., 'approvals')).

7.3 RepoRule configuration

Rules are stored per repository with trigger, action, severity, and optional scope columns. Managed via settings UI / server actions guarded by canManageRules (owner or admin). Disabled rules are skipped by evaluateRepoRules.

8. Integration with GitHub Sync

lib/github-sync.ts is the sole orchestrator that runs the governance pipeline in production. Entry points:

  • syncGitHubPullRequest — single PR by number (webhook-driven)
  • syncGitHubRepository — all open PRs for one repo
  • syncGitHubInstallation — all installation repos
  • backfillStaleGitHubRepositories — stale repo refresh

8.1 Agent inference

agentSourceHeuristic
cursorAuthor, title, or branch contains "cursor"
codexContains "codex"
claude_codeContains "claude"
copilotContains "copilot"

unknownagent/, -bot, or [ai] in combined string
manualDefault when no agent markers match

inferAiAssisted returns true for any non-manual source.

8.2 Usage metering

Each unique repositoryId:pullNumber:headSha consumes one PR check against plan limits via recordPrChecks. Repeat syncs for the same SHA are idempotent for billing (canRunPrCheck allows re-runs when usage row exists).

8.3 GitHub check run output

When the org plan includes githubComments, sync publishes an AgentGate check run with risk score, level, test gap status, CI status, and approval status. Failures to publish are logged but do not roll back persisted governance data.

8.4 Post-sync AI review

After persistence, enqueueAiReviewJob queues optional LLM analysis. This job does not mutate risk scores, rules, or approval state — it is a parallel advisory channel documented separately.

9. Caveats

TopicDetail
Heuristic, not semantic Risk and test gap use path regexes only. Renamed or unconventional directory layouts may miss or false-positive.
CI not wired on sync ciStatus is stored as unknown during sync; failing_ci signals/rules need explicit CI integration.
Labels empty on sync evaluateRepoRules receives labels: []; label-scoped rules never match until labels are fetched.
AI-assisted by string match Agent detection is substring heuristics on author/title/branch — not cryptographically verified agent identity.
Approval reset on new SHA New commits clear prior approval when approval is still required; reviewers must re-approve.
Violations replaced each sync resolved state on violations is lost on resync because rows are deleted and recreated.
Plan gating Recording approvals and GitHub check output require Team+ entitlements; scoring still runs on all plans within PR check limits.
Separate from LLM review AI review jobs may comment on code quality but do not change deterministic governance outputs.
block_merge is logical Sets approval requirement in AgentGate; actual GitHub branch protection merge blocking is external.
