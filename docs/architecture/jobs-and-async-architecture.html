MergeAttest — Jobs & Async Architecture

How background work is queued, authenticated, retried, and executed on a serverless Next.js deployment. MergeAttest does not run an in-app queue server (Redis, BullMQ, etc.); durable rows in PostgreSQL plus external cron hitting /api/jobs/* drive async processing. 1. Overview

MergeAttest treats PostgreSQL as the job queue. When work cannot finish inside a single HTTP request — or when it should survive process restarts — the app writes a row and returns. An external scheduler (cron, Vercel Cron, GitHub Actions, etc.) periodically calls protected POST /api/jobs/* routes to drain pending rows in bounded batches.

Three job runners exist today:

  1. GitHub webhooks — replay queued or failed webhook deliveries
  2. AI PR reviews — process AiReviewJob rows (guardrails only; model execution disabled)
  3. Retention — purge aged audit, webhook, billing, and export artifacts

The inbound GitHub webhook route (/api/github/webhook) also uses Next.js after() to kick off immediate processing of a single delivery after the HTTP response, while still persisting the delivery row for durability and cron retry.

No Redis required Queue state lives in GitHubWebhookDelivery and AiReviewJob tables. Cron is an operational dependency, not an application dependency at runtime.
Cron is required in production Without scheduled job runner calls, failed webhooks stay failed, AI review jobs stay queued, and retention warnings accumulate. See docs/operations/OPERATIONS_RUNBOOK.md.

3. Job Endpoints

All job routes are POST only. They bypass browser CSRF checks in proxy.ts because external cron callers cannot satisfy same-origin headers.

Endpoint Handler Query params Response shape
POST /api/jobs/github-webhooks processQueuedGitHubWebhookDeliveries limit — default 25, max 100 { processed, failed, skipped }
POST /api/jobs/pr-reviews processQueuedAiReviewJobs limit — default 25, max 100 (parseJobLimit) { processed, blocked, failed, skipped }
POST /api/jobs/retention cleanupOperationalData — { auditEventsDeleted, webhookDeliveriesDeleted, billingEventsDeleted, auditExportsDeleted }

Each route calls authorizeJobRequest() first, then logs completion via logEvent() with area jobs.

4. Auth (lib/job-auth.ts)

Job runners authenticate with a shared secret, not a user session. The caller must send: 

Authorization: Bearer {JOB_RUNNER_SECRET}
Condition Result
JOB_RUNNER_SECRET unset, non-production allow Request proceeds (dev convenience)
JOB_RUNNER_SECRET unset, production 503 Job runner secret is not configured.
Bearer token matches secret allow
Wrong or missing Bearer token (secret configured) 401 Invalid job runner token.

See also authentication architecture §8 for how job auth fits alongside webhook HMAC and session auth.

5. GitHub Webhook Queue

5.1 Ingest (app/api/github/webhook/route.ts)

  1. Verify x-hub-signature-256 via verifyGitHubWebhook().
  2. Read x-github-event and x-github-delivery.
  3. enqueueGitHubWebhookDelivery() — upsert row, store raw body in metadata.
  4. Return 202 when queued, 200 for duplicates or demo mode.
  5. In live mode with a delivery id, schedule after() to call processQueuedGitHubWebhookDeliveries({ deliveryId, limit: 1 }).

5.2 Delivery lifecycle (lib/github-webhooks.ts)

Status Meaning
queued Waiting for worker
processing Attempt in flight (attemptCount incremented)
processed Successfully handled (PR sync, checks, etc.)
failed Error; may retry when nextRetryAt elapses
ignored Event not actionable (installation missing, unsupported event)

5.3 Batch worker selection

processQueuedGitHubWebhookDeliveries() selects rows where:

  • status = 'queued', or
  • status = 'failed' and (nextRetryAt <= now or nextRetryAt is null)

Ordered by createdAt asc, capped by limit (default 10 inside the library; route defaults to 25). Missing raw payload in metadata marks the row failed with a computed nextRetryAt.

5.4 Downstream effects

Successful PR event processing calls syncGitHubPullRequestRecord(), which may record usage, publish check runs, and call enqueueAiReviewJob(). See GitHub integration architecture for the full sync pipeline.

6. AI Review Queue

6.1 Enqueue (lib/jobs/pr-review-lifecycle.ts)

enqueueAiReviewJob() runs during PR sync when:

  • Prisma is available and headSha is present
  • Repository AI reviews are enabled (shouldEnqueueAiReview)
  • No existing row for the computed reviewKey

reviewKey = {organizationId}:{repositoryId}:{pullNumber}:{headSha}. queueJobId = getQueueJobId(PR_REVIEW_JOB_NAME, reviewKey) → pr_review:{reviewKey} unless overridden.

6.2 Terminal statuses

isTerminalAiReviewStatus() treats these as final — the worker will not re-process them:

Status Typical cause
blocked Missing OpenRouter credentials
skipped AI disabled, empty diff, or model execution not enabled yet
completed Successful review (future)
failed Unhandled exception during worker run

Non-terminal: queued, in_progress. The cron worker only selects status = 'queued'.

6.3 Worker (lib/jobs/pr-review-worker.ts)

processQueuedAiReviewJobs() for each job:

  1. Transition to in_progress, increment attemptCount.
  2. Re-check repository AI settings, OpenRouter credential, GitHub diff availability.
  3. Apply diff path filters (filterDiffFiles).
  4. Currently marks jobs skipped after guardrails pass — AI model execution is not enabled yet.
  5. On exception, sets failed with errorMessage.
No webhook-style backoff for AI jobs Failed AI jobs stay terminal. New work for the same commit requires a new headSha (new reviewKey). Queued jobs are picked up on the next cron invocation with no nextRetryAt field.

7. Retention Job (lib/retention.ts)

cleanupOperationalData() runs via POST /api/jobs/retention. Recommended cadence: daily. No batch limit — one invocation processes all eligible rows.

Target Criteria Retention window
AuditEvent Per organization, by plan auditRetentionDays from plan entitlements (null = skip)
GitHubWebhookDelivery status in processed, ignored 30 days
BillingWebhookEvent status in processed, ignored 365 days
AuditExport All exports 30 days

Without PostgreSQL (demo mode), returns zero counts for all fields without throwing.

8. Idempotency Keys

Async and metering paths rely on unique constraints so duplicate deliveries or syncs do not double-charge or double-enqueue.

Entity Key field Format / source Effect
GitHubWebhookDelivery deliveryId GitHub x-github-delivery header UNIQUE; replays update existing row; processed deliveries short-circuit
AiReviewJob reviewKey {orgId}:{repoId}:{pullNumber}:{headSha} UNIQUE; enqueueAiReviewJob returns existing job on conflict
UsageRecord sourceKey {repositoryId}:{pullNumber}:{headSha} via getPrCheckSourceKey() UNIQUE per org + metric + period; prevents duplicate PR check metering

8.1 Queue job id helper (lib/jobs/queue.ts)

export const PR_REVIEW_JOB_NAME = 'pr_review'

export function getQueueJobId(jobName: string, key: string) {
  return `${jobName}:${key}`
}

Stored on AiReviewJob.queueJobId for traceability; not a separate queue table primary key.

9. Retry Semantics

9.1 GitHub webhook exponential backoff

Defined in retryDelayMs(attemptCount) inside lib/github-webhooks.ts: 

Math.min(60_000 * 2 ** Math.max(0, attemptCount - 1), 15 * 60_000)
Attempt Delay before next retry
1 1 minute
2 2 minutes
3 4 minutes
4 8 minutes
5+ 15 minutes (cap)

On failure, nextRetryAt is set from the attempt start time. The cron worker picks up failed rows when nextRetryAt <= now. Manual retry from GitHub settings or calling /api/jobs/github-webhooks also drains eligible rows.

9.2 AI review jobs

  • Only queued jobs are candidates.
  • Exceptions during processing → terminal failed (no automatic re-queue).
  • Prerequisite failures → terminal blocked or skipped.

9.3 Retention

Idempotent deletes — safe to run daily; missing rows are a no-op.

10. Serverless Caveats

Topic Detail
Short-lived requests Each job invocation processes at most limit items (max 100). Large backlogs require multiple cron ticks, not one long-running worker.
No in-process workers Nothing polls the database inside the Next.js process between HTTP requests. All async drain happens when cron hits job routes or when after() runs post-response on webhook ingest.
after() scope Immediate webhook processing runs once per delivery with limit: 1. Failures still rely on cron + nextRetryAt; the client already received 202.
Demo mode without DB Job routes authorize but workers return empty summaries when getPrismaClient() is null.
Rate limits Job routes are exempt from CSRF but still subject to edge rate limits unless configured otherwise. Cron should use a stable egress IP if rate limiting by IP.
Concurrent cron Two overlapping cron invocations may race on the same row; status transitions and unique keys limit duplicate side effects but duplicate attempts increment attemptCount.

11. Operations (Cron)

Configure scheduled HTTPS POST calls with Authorization: Bearer $JOB_RUNNER_SECRET. Full runbook: docs/operations/OPERATIONS_RUNBOOK.md.

Endpoint Recommended cadence Monitor
/api/jobs/github-webhooks Every 1–5 minutes Non-zero failed; failed deliveries in /api/diagnostics
/api/jobs/pr-reviews Every 1–5 minutes Stale queued jobs; non-zero blocked / failed
/api/jobs/retention Daily Retention warnings in diagnostics; job log errors

11.1 Example cron invocation

curl -X POST "https://app.example.com/api/jobs/github-webhooks?limit=50" \
  -H "Authorization: Bearer $JOB_RUNNER_SECRET"

11.2 Incident triage (summary)

  1. Check /api/diagnostics as workspace owner/admin.
  2. Review failed webhook deliveries in GitHub settings or trigger retry via job endpoint.
  3. For stale AI jobs, call /api/jobs/pr-reviews and inspect blocked/failed counts.
  4. If retention warnings persist, call /api/jobs/retention and inspect logs.
