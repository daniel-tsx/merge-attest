02 Architecture map

Everything enters through the Vercel edge (proxy.ts), which gates pages and API/webhook/job routes alike. Server-side domain logic in lib/ is the only thing that talks to PostgreSQL and to external services. Dashed boxes/arrows are dormant, optional, or intentionally disabled today.

03 Core request flow

The default path for an authenticated page view.

Authenticated page request read
User · Browser → proxy.ts session gate → RSC page.tsx → app-data.ts org scope → Prisma → PostgreSQL → HTML + client islands → Vercel Analytics
API / webhook / job request write
Inbound caller → proxy.ts rate limit + origin → route handler → auth: session / Bearer / signature → domain service + zod → Prisma write → JSON log on error

06 Layer summary

What each layer does, where it lives, and what to watch.

Client browser

Public marketing/auth pages and the authenticated app shell. Server-rendered by default; small client islands for charts, filters, command palette, and toasts.

app/page.tsx, app/(auth), app/dashboard …, components/app/*, components/ui/*

Edge & app vercel / next.js

proxy.ts is the single gate (session, rate limit, CSRF, headers). Behind it: ~22 route handlers, server actions, and RSC pages. Domain logic lives in lib/.

proxy.ts, app/api/**/route.ts, app/**/actions.ts, lib/*.ts

Authentication better auth

Email/password sessions via cookie; org membership maps to roles (owner / admin / member / viewer). Protected routes enforced at the edge; platform admin gated by an allowlist.

lib/auth.ts, lib/auth/session.ts, app/api/auth/[...all], lib/admin/access.ts

Data postgres / prisma

Multi-tenant schema rooted at Organization; every read is org-scoped through app-data.ts. Dev can fall back to demo data; production fails closed without a database.

prisma/schema.prisma, prisma/migrations, lib/data/app-data.ts, lib/demo-data.ts

External services server-side

Reached only from lib/: GitHub App (core), Better Auth Infra, Resend (optional), OpenRouter (disabled), Lemon Squeezy (dormant). See the inventory above.

lib/github*.ts, lib/email.ts, lib/ai/*, lib/billing.ts

Security cross-cutting

Auth + role + plan entitlements server-side; CSRF/origin and in-memory rate limiting in proxy.ts; webhook signature verification; Bearer-secured jobs; encrypted BYOK keys; env validated in prod.

lib/security.ts, lib/rate-limit.ts, lib/entitlements.ts, lib/env.ts, lib/ai/credentials.ts

Observability logs / analytics

Structured JSON logs to stdout (captured by the Vercel log drain) plus Vercel Analytics. Diagnostics and health endpoints for triage. No error-tracking or product-analytics SaaS.

lib/observability.ts, app/api/diagnostics, app/api/health

08 Gaps & review notes

Real gaps found while reviewing the code — several are deliberate for the free early-access launch, but worth tracking.

Rate limiting is in-memory

lib/rate-limit.ts is per-instance, so limits don’t span serverless invocations. Fine for a soft guard; a shared store (e.g. Upstash) would be needed for hard enforcement at scale.

AI execution disabled

The OpenRouter path is fully queued and guardrailed but ends in a “skipped” status — no model is actually called yet. Treat AI output as not-live.

No error-tracking SaaS

Errors go to structured JSON logs only (no Sentry/equivalent), and there is no product analytics beyond Vercel Analytics. Diagnosing issues relies on the log drain + /api/diagnostics.

Cron is an external dependency

No vercel.json cron in the repo. Jobs (webhooks, AI, retention) only run if an external scheduler hits /api/jobs/* — required in production.

Database host not pinned

Code targets generic pooled PostgreSQL; Neon/Supabase appear only as examples in docs. Confirm the actual production provider when reasoning about pooling/limits.

No notification delivery

Resend handles auth/invite email only; there is no Slack/email alerting on governance events. @better-auth/sso is a dependency but enterprise SSO/SCIM is not wired.
