1. Overview

AgentGate is a multi-tenant SaaS control center for AI-assisted pull request governance. All business data is scoped to an Organization (workspace). PostgreSQL is the system of record; Prisma 7 is the ORM with a driver adapter (@prisma/adapter-pg).

Core responsibilities of the database layer:

  • Identity and sessions (Better Auth tables)
  • Tenant workspaces, memberships, and team invites
  • GitHub-connected repositories and pull requests with governance signals
  • Rules, violations, approvals, and audit evidence
  • Plan entitlements, usage metering, and Lemon Squeezy billing state
  • Durable webhook delivery queues and AI review job lifecycle
  • Encrypted BYOK AI provider credentials
Design principle Business reads are organization-scoped via lib/data/app-data.ts. Cross-tenant queries exist only in lib/admin/admin-data.ts, gated by ADMIN_EMAILS.

Client initialization

getPrismaClient() in lib/prisma.ts returns null when DATABASE_URL is unset. In production, validateProductionEnv() runs first and fails closed if required env vars are missing. The client is cached on globalThis keyed by connection string so hot reloads do not leak connections. 

// lib/prisma.ts — simplified
const adapter = new PrismaPg({ connectionString: databaseUrl })
globalForPrisma.agentGatePrisma = new PrismaClient({ adapter })

3. Architecture

3.1 Multi-tenant boundary

The tenant root is Organization. Nearly every business table carries an organizationId foreign key with onDelete: Cascade. Application queries filter by the current session's organization ID — never by user ID alone for business data.

┌─────────────────────────────────────────────────────────────────┐ │ PostgreSQL (single database) │ ├─────────────────────────────────────────────────────────────────┤ │ Auth layer (Better Auth) │ │ User ── OrganizationMember ── Organization │ │ Session, Account, Verification │ ├─────────────────────────────────────────────────────────────────┤ │ Core domain (org-scoped) │ │ Organization ── Repository ── PullRequest │ │ │ ├── PullRequestFile │ │ │ ├── RiskSignal │ │ │ ├── TestGapAnalysis │ │ │ ├── RuleViolation │ │ │ ├── Approval │ │ │ └── AiReviewJob │ │ └── RepoRule │ ├─────────────────────────────────────────────────────────────────┤ │ Operations & billing │ │ UsageRecord, Plan, GitHubWebhookDelivery, BillingWebhookEvent │ │ AuditEvent, AgentActivity, AuditExport │ │ AiProviderCredential, RepositoryReviewSettings, ApiKey │ └─────────────────────────────────────────────────────────────────┘

3.3 Demo vs live data mode

When DATABASE_URL is missing or queries fail in development, reads fall back to lib/demo-data.ts via queryWithDemoFallback(). Production never falls back — it throws if the database is unavailable. 

// lib/data/app-data.ts — behavior summary
if (!client) {
  if (isProduction()) throw new Error('Database access is required in production.')
  return fallback()  // demo data
}
try { return await query(client) }
catch (error) {
  if (isProduction()) throw error
  return fallback()
}

4.2 Enumerations

The schema defines 20+ PostgreSQL enums for typed domain values — roles, billing status, risk levels, rule triggers/actions, AI review status, audit event types, etc. Enums are migrated explicitly in SQL (CREATE TYPE ... AS ENUM) and referenced by Prisma models. Adding enum values requires a migration.

4.3 Referential integrity

  • Cascade deletes from Organization → most child tables (data isolation on org removal).
  • SetNull on optional user references (reviewer, invite acceptor) to preserve history.
  • PullRequestFile, RiskSignal, etc. cascade from PullRequest — no direct org FK on leaf tables.
  • Webhook/billing event tables use optional organizationId with SetNull for events received before org resolution.

4.4 Denormalization

  • PullRequest.organizationId — duplicated from repository for org-scoped queries without joins.
  • RepoRule.organizationId — enables org-wide rule queries.
  • Repository.monthlyPrCheckUsage — counter field (alongside authoritative UsageRecord aggregation).
  • Repository.activeRulesCount — maintained on rule changes.

5. Data Flow

5.1 Read path (UI)

  1. Request hits proxy.ts (session cookie, rate limits).
  2. Server Component calls ensureCurrentUserOrganization() → resolves org from session.
  3. Page calls app-data functions with organizationId.
  4. Prisma query runs with where: { organizationId } (+ filters).
  5. Rows are mapped to UI types (mapPullRequest, etc.) and rendered.

5.2 User signup & org provisioning

  1. Better Auth creates User (+ Account with password hash).
  2. On first authenticated request, ensureCurrentUserOrganization() checks OrganizationMember.
  3. If none exists, creates Organization with slug {slugified-name}-{userId-prefix} and owner membership.
  4. Default planKey = "free", billingStatus = active.

5.3 GitHub webhook → PR sync (write path)

GitHub POST /api/github/webhook │ ├─ Verify HMAC signature ├─ Insert GitHubWebhookDelivery (deliveryId unique → skip duplicates) ├─ Resolve Organization by githubInstallationId │ └─ Queue processor / syncGitHubPullRequest() │ ├─ canRunPrCheck() — entitlement + UsageRecord idempotency ├─ Fetch PR files from GitHub API ├─ calculateRisk(), detectTestGap(), evaluateRepoRules() ├─ pullRequest.upsert (by repositoryId + number) ├─ Replace child rows: files, riskSignals, testGap, violations ├─ recordPrChecks() with sourceKey = repo:pr:sha ├─ Write AuditEvent + AgentActivity ├─ publishAgentGateCheckRun() (if plan allows) └─ enqueueAiReviewJob() (if repo AI settings enabled)

5.4 Usage metering

PR checks are metered monthly in UTC calendar months via UsageRecord: 

// lib/usage.ts
periodStart = UTC first day of month
periodEnd   = UTC first day of next month
metric      = "pr_checks"

Idempotency: composite unique key [organizationId, metric, periodStart, sourceKey] where sourceKey encodes repository + PR number + head SHA. Re-syncing the same commit does not double-count; a new push (new SHA) consumes another check if under limit.

5.5 Billing webhooks

  1. Lemon Squeezy POST → verify signature.
  2. Insert BillingWebhookEvent by deliveryId (dedupe).
  3. Update Organization subscription fields and planKey.

5.6 AI review job lifecycle

AiReviewJob.reviewKey = {orgId}:{repoId}:{pullNumber}:{headSha} — ensures one job per PR commit. Status transitions: queued → in_progress → completed|failed|skipped|blocked. Worker code lives in lib/jobs/pr-review-worker.ts; model execution is intentionally disabled at time of writing — lifecycle and GitHub output boundaries are in place.

5.6 Approval writes

POST /api/pull-requests/[id]/approval creates an Approval row, updates PullRequest.approvalStatus, writes AuditEvent, and optionally posts GitHub comments/check runs when entitlements allow.

6.6 Seed behavior

prisma/seed.ts uses the same PrismaPg adapter as the app. It deletes all rows in dependency order before inserting demo data — destructive on every pnpm db:seed run. Do not run seed against production databases.

7.2 Tables without explicit indexes

Index gaps to be aware of The following high-volume tables are queried by organizationId but have no dedicated index in the current schema:
  • AuditEvent — filtered by org + createdAt range in audit log UI and retention cleanup
  • AgentActivity — filtered by org, ordered by timestamp DESC
  • Approval, RuleViolation, PullRequestFile, RiskSignal — accessed via PR includes (join from indexed PR)
At scale, consider adding @@index([organizationId, createdAt]) on AuditEvent and @@index([organizationId, timestamp]) on AgentActivity.

7.3 Foreign keys

Prisma generates foreign key constraints automatically. All org-scoped FKs use ON DELETE CASCADE except nullable user/org references which use SET NULL.

8. Optimization & Query Patterns

8.1 Organization-scoped reads

Always include organizationId in where clauses for tenant tables. The app never relies on ID-only lookups for business entities without org verification (except admin module).

8.2 Eager loading

PR detail pages use Prisma include to fetch nested relations in one round trip: files, riskSignals, testGapAnalysis (+ suggestions), ruleViolations (+ rule), approvals, comments, aiReviewJobs. Avoid N+1 by batching includes at the list/detail query level.

8.3 React request deduplication

getServerSession is wrapped in React cache() so multiple server components in one request share a single auth lookup.

8.4 Connection pooling

On serverless (Vercel), use a pooled connection string (e.g. Neon, Supabase pooler, or PgBouncer). The Prisma PG adapter opens connections via the provided URL — pool settings are controlled by the connection string and platform, not in application code.

8.5 Write amplification on PR sync

Each PR sync deletes and recreates child rows (files, signals, violations) rather than diffing. This simplifies correctness but increases write volume. Acceptable at current scale; consider upsert/diff strategies if sync frequency grows.

8.6 Usage aggregation

getPrCheckUsage() uses aggregate({ _sum: { quantity } }) over UsageRecord for the current month — indexed via [organizationId, metric, periodStart]. History queries fetch recent rows and bucket in application code.

8.7 Webhook queue polling

Retry worker queries GitHubWebhookDelivery where status is pending/failed and nextRetryAt <= now, using the nextRetryAt index. Exponential backoff capped at 15 minutes.

8.8 JSON columns

JSON fields (metadata, providerMetadata, features, filters) are not indexed. Filtering happens in application code after fetch, or JSON is used for display/export only — not for indexed queries.

9. Technical Caveats

Demo fallback is dev-only Missing or failing DB in development silently serves static demo data. This can mask schema drift or broken queries during local work. Run against a real Postgres instance before shipping.
Topic Detail
Single-org session ensureCurrentUserOrganization() returns the user's first membership (orderBy: createdAt asc). Multi-org switching is not implemented in session context.
Auth without database lib/auth.ts omits the Prisma adapter when getPrismaClient() is null. Auth persistence requires PostgreSQL.
Seed is destructive pnpm db:seed wipes all tables. Never run on production.
Paddle → Lemon Squeezy Migration 20260518173000 drops Paddle columns/tables. Existing Paddle subscriber IDs are not migrated — manual Lemon Squeezy backfill required.
Nullable sourceKey in UsageRecord The unique constraint includes sourceKey which can be NULL in PostgreSQL (NULLs are distinct in unique indexes). App code always passes sourceKey for PR checks.
AI model execution AiReviewJob rows are created and transitioned, but the worker skips actual LLM calls — guardrail in pr-review-worker.ts.
ApiKey lookup No index on hashedKey — validation likely scans by prefix or uses a separate lookup strategy.
Plan table dual use Plan rows are seeded per organization (organizationId set) rather than a global catalog table. Plan definitions also live in lib/plans.ts and lib/entitlements.ts (code is authoritative for enforcement).
UTC usage periods Monthly billing periods use UTC month boundaries, not org timezone.
Prisma 7 driver adapter Requires @prisma/adapter-pg; standard Prisma binary engine connection string alone is not used. Generated client lives at lib/generated/prisma.
Cross-tenant admin lib/admin/admin-data.ts intentionally queries all orgs. Must always be preceded by requirePlatformAdmin().

10. Data Retention & Cleanup

cleanupOperationalData() in lib/retention.ts is invoked by the job runner. Retention is plan-aware for audit data and fixed for operational tables.

Data Retention rule Mechanism
AuditEvent Per plan: 7 / 30 / 180 / 365 days; unlimited for Enterprise deleteMany where createdAt < cutoff per org
GitHubWebhookDelivery 30 days for processed/ignored Global delete (not org-scoped)
BillingWebhookEvent 365 days for processed/ignored Global delete
AuditExport 30 days (metadata only; CSV is streamed, not stored) Global delete

PR data, repositories, and governance records are not automatically purged — only audit and operational queue metadata expire.

11. Security Considerations

11.1 Tenant isolation

  • All app reads/writes filter by session organization ID.
  • Cascade deletes prevent orphaned cross-tenant references.
  • Admin cross-tenant access requires explicit email allowlist (ADMIN_EMAILS).

11.2 Secrets at rest

  • AiProviderCredential.encryptedKey — AES-256-GCM via lib/ai/credentials.ts; key derived from AI_PROVIDER_ENCRYPTION_KEY or BETTER_AUTH_SECRET.
  • ApiKey.hashedKey — stored hashed; plaintext shown once at creation.
  • Passwords live in Account.password (Better Auth managed hashing).

11.3 Webhook integrity

  • GitHub webhooks: HMAC-SHA256 with GITHUB_WEBHOOK_SECRET.
  • Lemon Squeezy: signature verification with LEMON_SQUEEZY_WEBHOOK_SECRET.
  • Both use durable delivery tables for idempotency before side effects.

11.4 Production env validation

validateProductionEnv() in lib/env.ts enforces required secrets including DATABASE_URL, BETTER_AUTH_SECRET, BETTER_AUTH_API_KEY, and integration keys before database client creation.
