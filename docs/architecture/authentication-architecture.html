1. Overview

Auteur uses Better Auth for email/password authentication with optional email verification and password reset via Resend. Sessions are cookie-based; there is no JWT handed to the client for API calls. The app does not implement enterprise SSO, OAuth social login, or SCIM (see docs/strategy/ENTERPRISE_PLACEHOLDERS.md).

Authentication is split into three concerns:

  1. Authentication — Is this a signed-in user? (Better Auth session cookie)
  2. Workspace context — Which organization and role? (ensureCurrentUserOrganization)
  3. Authorization — Is this action allowed for that role? (lib/collaboration.ts helpers)
Fail closed in production Missing auth config, database, or invalid sessions block real behavior. Development can bypass the page auth gate when PostgreSQL is not configured (demo UI only).

3. Architecture Layers

Browser │ ▼ proxy.ts ← cookie presence, rate limits, CSRF, security headers │ ├─ Public paths (/, /sign-in, /sign-up, /forgot-password, /reset-password) ├─ /api/* ← passes through (handler validates auth) └─ App pages ← redirect to /sign-in if no session cookie │ ▼ app/api/auth/[...all]/route.ts ← Better Auth HTTP API (login, logout, verify, etc.) │ ▼ lib/auth.ts ← betterAuth({ database, emailAndPassword, plugins }) │ ▼ PostgreSQL ← User, Session, Account, Verification ── After sign-in ── Server Component / API route │ ├─ getServerSession() ← auth.api.getSession({ headers }) [React cache] ├─ ensureCurrentUserOrganization()← session + OrganizationMember (+ auto-provision) └─ getCurrentOrganization() ← org context + dataMode for UI [React cache]

3.1 Two-tier session check

The edge layer (proxy.ts) only checks whether a session cookie exists via getSessionCookie(). It does not validate the token against the database. Full validation happens in server code through auth.api.getSession(), which reads the cookie, looks up the Session row, and returns the user or null.

Cookie presence ≠ valid session An expired or revoked session cookie may pass the edge gate briefly until getServerSession() runs. API routes and server actions must always resolve the session explicitly; never assume the edge gate proves identity.

3.2 Request-scoped caching

getServerSession, getPlatformAdminContext, and getCurrentOrganization are wrapped in React cache() so multiple server components and layout segments in one request share a single auth lookup.

4. Authentication Flows

4.1 Sign up

  1. User submits name, email, password on /sign-up (client component).
  2. signUp.email() from lib/auth-client.ts calls Better Auth API.
  3. Better Auth creates User + Account (password hash).
  4. If Resend is configured (RESEND_API_KEY + EMAIL_FROM), verification email is sent and sign-in may require verified email.
  5. Client calls POST /api/onboarding/organization → ensureCurrentUserOrganization() creates default free workspace if needed.
  6. Redirect to callbackUrl or /dashboard via safeRelativeRedirect.

4.2 Sign in

  1. User submits email/password on /sign-in.
  2. signIn.email() validates credentials via Better Auth.
  3. Better Auth creates/updates Session row and sets session cookie.
  4. POST /api/onboarding/organization ensures workspace exists.
  5. Redirect to safe relative callbackUrl (open-redirect protection in lib/redirects.ts).

4.3 Email verification

Controlled by whether transactional email is configured (isEmailDeliveryConfigured() in lib/email.ts):

  • requireEmailVerification — enabled when Resend is configured
  • sendOnSignUp / sendOnSignIn — verification emails on those events
  • Tokens stored in Verification table; indexed by identifier

Without Resend, email verification is disabled and sign-up/sign-in work without verification in dev.

4.4 Password reset

  1. User requests reset on /forgot-password.
  2. Better Auth sends email with reset link via sendResetPassword callback.
  3. User sets new password on /reset-password.
  4. revokeSessionsOnPasswordReset: true — all existing sessions invalidated.

4.5 Sign out

Client calls signOut() from auth client → Better Auth clears session cookie and removes/invalidates the Session row.

4.6 Team invite acceptance

  1. Invite link: GET /api/team/invites/accept?token=...
  2. Requires authenticated session; redirects to sign-in with callbackUrl if absent.
  3. Invite token is hashed (SHA-256) before DB lookup — raw token only appears in URL/email.
  4. Email must match invite recipient (case-insensitive).
  5. POST creates/updates OrganizationMember and marks invite accepted.

Note: accepting an invite adds membership to the invited organization, but session context still resolves to the user's first membership unless multi-org switching is added.

Session.ipAddress, userAgent Optional audit metadata

5.1 Workspace binding

After session validation, ensureCurrentUserOrganization() loads the user's earliest OrganizationMember row (orderBy: createdAt asc). If none exists, it auto-creates an Organization with slug {slugified-name}-{userId-prefix} and owner role.

getCurrentOrganization() in lib/data/app-data.ts maps this to UI context including dataMode: 'live' | 'demo'.

5.2 Auth without database

When getPrismaClient() returns null, lib/auth.ts omits the Prisma adapter entirely. Better Auth cannot persist users or sessions — auth pages exist but credentials are not stored. Combined with proxy.ts dev bypass, the UI remains usable in demo mode without PostgreSQL.

6. Authorization (RBAC)

Organization roles are stored on OrganizationMember.role: owner, admin, member, viewer. Permission checks live in lib/collaboration.ts and are enforced in server actions and API routes — not in a centralized middleware.

Capability owner admin member viewer
Manage team / invites ✓ ✓
Manage settings (AI keys) ✓ ✓
Manage billing ✓
Sync GitHub / repos ✓ ✓
Manage rules / AI review settings ✓ ✓
Export audit log ✓ ✓
Record PR approvals ✓ ✓ ✓
Comment on PRs ✓ ✓ ✓
Read dashboards / PRs ✓ ✓ ✓ ✓

6.1 Enforcement patterns

  • Server actions — call getCurrentOrganization(), then canManage*(role); redirect with ?status=forbidden on denial.
  • API routes — call ensureCurrentUserOrganization(); return 401 if null; check role helpers before mutations.
  • Plan entitlements — separate from RBAC; enforced in lib/entitlements.ts (e.g. audit export, GitHub output).

6.2 Platform admin (cross-tenant)

Operator console at /admin/* uses a different authorization model: email allowlist via ADMIN_EMAILS env var, not organization role.

  • requirePlatformAdmin() in app/admin/layout.tsx — returns 404 for non-admins (least disclosure).
  • getPlatformAdminContext() — cached per request; checks session email against allowlist.
  • Admin server actions re-check context?.isAdmin before mutations.
  • Data reads go through lib/admin/admin-data.ts (intentionally cross-tenant).

6.3 Tenant isolation on reads

All normal app data reads include organizationId from session context. Resource IDs alone are never sufficient — handlers verify the entity belongs to the current organization.

7. Edge Security (proxy.ts)

Next.js middleware equivalent runs on almost all routes (excluding static assets). Responsibilities:

7.1 Page auth gate

Condition Behavior
Public path prefix match Allow
/api/* Allow (handler auth)
Dev + no DATABASE_URL Allow app pages without cookie
Session cookie present Allow
Otherwise Redirect to /sign-in?callbackUrl=...

7.2 CSRF / origin validation

Mutating API requests (POST, PUT, PATCH, DELETE) must pass same-origin check via Origin or Referer header (lib/security.ts).

Exemptions (external callers cannot satisfy browser origin):

  • /api/auth/* — Better Auth endpoints
  • /api/jobs/* — Bearer token job runner
  • Paths containing /webhook — GitHub, Lemon Squeezy

7.3 Rate limiting

In-memory sliding window per IP + method + pathname (lib/rate-limit.ts):

Rule Limit Applies to
auth 30 / minute /api/auth/*
webhook 300 / minute Paths containing /webhook
mutation 90 / minute Non-GET API routes
public 120 / minute Everything else
Rate limits are process-local Buckets live in a module-level Map. On serverless/multi-instance deployments, limits are per instance, not global. Use an edge KV or Redis for shared limits at scale.

7.4 Security headers

Applied to every response via applySecurityHeaders():

  • X-Content-Type-Options: nosniff
  • X-Frame-Options: DENY
  • Referrer-Policy: strict-origin-when-cross-origin
  • Permissions-Policy — camera, microphone, geolocation disabled
  • Cross-Origin-Opener-Policy: same-origin
  • Cross-Origin-Resource-Policy: same-origin
  • Strict-Transport-Security — production only

7.5 Open redirect protection

safeRelativeRedirect() only allows relative paths starting with /, rejects //, backslashes, and control characters. Used for post-login redirects and invite callbacks.

8. Non-User Authentication

Not all requests are browser sessions. Other auth mechanisms:

Actor Mechanism Module
GitHub webhooks HMAC-SHA256 x-hub-signature-256 vs GITHUB_WEBHOOK_SECRET lib/github.ts → verifyGitHubWebhook()
Lemon Squeezy webhooks HMAC signature verification lib/lemon-squeezy-webhooks.ts
Job runner (cron) Authorization: Bearer {JOB_RUNNER_SECRET} lib/job-auth.ts
Platform admin Session + ADMIN_EMAILS allowlist lib/admin/access.ts

8.1 Job runner endpoints

  • POST /api/jobs/github-webhooks — process queued webhook deliveries
  • POST /api/jobs/pr-reviews — AI review worker
  • POST /api/jobs/retention — data retention cleanup

In development without JOB_RUNNER_SECRET, requests are allowed. In production, missing secret returns 503; wrong token returns 401.

8.2 GitHub webhook dev mode

Without GITHUB_WEBHOOK_SECRET, verification succeeds in non-production (mode: 'demo') so local webhook testing works. Production requires the secret and rejects missing/invalid signatures with 401.

8.3 API keys (future / partial)

The schema includes an ApiKey model (prefix, hashedKey), and getApiKeyCount() exists in app-data, but there is no request-level API key authentication middleware in the current codebase. User-facing auth is session-only.

Verification Email verify + reset tokens identifier

10.1 Trusted origins

Better Auth trustedOrigins includes BETTER_AUTH_URL and https://dash.better-auth.com (Infra plugin). Cross-origin auth requests from untrusted origins are rejected by Better Auth.

11. Technical Caveats

Topic Detail
Single-org session Session always binds to the user's first organization membership. Multi-org switching is not implemented.
Edge vs server validation proxy.ts checks cookie presence only; always use getServerSession() for identity.
Dev demo bypass Without DB in dev, app pages load without login. Do not confuse with production behavior.
Local auth secret Dev uses hardcoded fallback secret if BETTER_AUTH_SECRET unset — never use in production.
No SSO / OAuth Email/password only. Enterprise SSO is planned placeholder only.
RBAC not centralized Each action/route checks permissions individually; easy to miss on new endpoints.
Admin 404 vs 403 Non-admin users hitting /admin see 404, not 403, by design.
In-memory rate limits Not shared across serverless instances; per-process only.
Invite + first org Accepting invite to org B does not switch session context away from org A until multi-org is built.
Password in Account table Better Auth stores hashed password on Account, not User.

13. Quick Reference — Request Checklist

When adding a new protected endpoint or server action:

  1. Is it a browser page? → proxy.ts handles coarse cookie gate.
  2. Resolve identity → getServerSession() or ensureCurrentUserOrganization().
  3. Check role → appropriate canManage*() from lib/collaboration.ts.
  4. Check plan → getPlanEntitlements() if feature-gated.
  5. Scope data → always filter by organizationId from session context.
  6. Mutating API from browser? → Origin check applies unless exempt.
  7. External webhook/job? → Use signature or Bearer auth, not session.
