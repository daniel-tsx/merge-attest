Auteur — GitHub Integration Architecture

1. Overview

Auteur integrates with GitHub through a GitHub App using @octokit/auth-app and octokit. Each workspace (Organization) stores a single githubInstallationId after the owner or admin completes the App install flow. Sync and webhook handlers use installation tokens to read repositories and pull requests, compute risk and rule violations, persist domain rows in PostgreSQL, and optionally publish Auteur check runs and AI review output back to GitHub.

The integration has four major paths:

  1. Install — OAuth-style redirect stores installation metadata on the org.
  2. Manual sync — Authenticated API routes pull installation repos and open PRs.
  3. Webhooks — GitHub POSTs signed events; deliveries are queued and processed asynchronously.
  4. Output — Check runs, managed comments, and inline review comments are published when entitled.
GitHub App install │ ▼ Organization.githubInstallationId │ ├─ Manual sync (POST /api/github/sync/*) │ └─ listInstallationRepositories → syncGitHubPullRequestRecord │ └─ Webhooks (POST /api/github/webhook) ├─ verifyGitHubWebhook (HMAC sha256) ├─ enqueueGitHubWebhookDelivery └─ after() → processQueuedGitHubWebhookDeliveries └─ sync / CI update / review / installation resync
Installation-scoped access All GitHub API calls use installation auth (getInstallationOctokit). The app never stores user OAuth tokens for repository access.

3. Install & Connect Flow

Settings UI (app/settings/github/page.tsx) │ ├─ createGitHubInstallationState(organizationId) ← HMAC-signed, 15 min TTL └─ getGitHubAppInstallUrl(state) ← requires GITHUB_APP_SLUG │ ▼ GitHub App install page │ ▼ GET /api/github/installation?installation_id=&state= │ ├─ ensureCurrentUserOrganization() ├─ canSyncGitHub(role) → owners/admins only ├─ verifyGitHubInstallationState(state, orgId) ├─ getGitHubInstallationMetadata(installationId) └─ prisma.organization.update({ githubInstallationId, githubAccountId, githubAccountLogin }) │ ▼ Redirect → /settings/github?connected=true

3.1 Persisted fields

On successful install callback, the organization row is updated with:

  • githubInstallationId — numeric installation ID from query string
  • githubAccountId — GitHub account ID of the installing account/org
  • githubAccountLogin — GitHub login of the installing account/org

An audit event (settings_changed) is recorded. Invalid or missing installation_id, failed state verification, or failed metadata lookup redirect to /settings/github?error=....

3.2 State parameter security

createGitHubInstallationState embeds organizationId, a random nonce, and expiresAt in a base64url payload signed with BETTER_AUTH_SECRET. The callback verifies signature, org match, and expiry before accepting the installation.

4. Manual Sync

4.1 Installation-wide sync

syncGitHubInstallation(organizationId) calls listInstallationRepositories and, for each GitHub repo:

  • Matches existing row by githubRepositoryId or owner/name
  • Respects plan repositoryLimit via canConsume for new repos
  • Upserts Repository with metadata (node ID, URL, default branch, visibility)
  • Syncs all open pull requests via syncPullRequestsForRepository

4.2 Single repository sync

syncGitHubRepository(repositoryId, organizationId) requires the org to have githubInstallationId, then syncs open PRs for that repo and updates connectedStatus and lastSyncedAt.

4.3 Backfill

backfillStaleGitHubRepositories finds connected repositories where lastSyncedAt is null or older than a threshold (default 60 minutes, limit 25) and runs syncGitHubRepository on each.

4.4 Pull request sync record

syncGitHubPullRequestRecord is the core per-PR pipeline:

  1. Usage gate — canRunPrCheck (see §9)
  2. Fetch files — listGitHubPullRequestFiles
  3. Inference — inferAgentSource, inferAiAssisted
  4. Analysis — calculateRisk, detectTestGap, evaluateRepoRules
  5. Approval state — getNextApprovalState preserves decisions on same headSha
  6. Upsert — PullRequest row
  7. Child rows — delete-and-recreate: PullRequestFile, RiskSignal, RuleViolation, TestGapAnalysis (+ suggestions)
  8. Side effects — audit event, enqueueAiReviewJob, recordPrChecks, optional publishAuteurCheckRun

4.5 Agent source inference

inferAgentSource scans author login, PR title, and head branch (lowercased):

Signal Source
cursor cursor
codex codex
claude claude_code
copilot copilot
devin devin
agent/, -bot, [ai] unknown
Otherwise manual

inferAiAssisted returns true when inferAgentSource(...) !== 'manual'.

5. Webhook Pipeline

GitHub POST /api/github/webhook │ ├─ Read raw body ├─ verifyGitHubWebhook(rawBody, x-hub-signature-256) │ ├─ HMAC-SHA256 with GITHUB_WEBHOOK_SECRET │ ├─ timingSafeEqual on "sha256=..." prefix │ ├─ Production + missing secret → 401 │ └─ Non-production + missing secret → demo mode (ok: true) │ ├─ enqueueGitHubWebhookDelivery({ deliveryId, event, rawBody }) │ ├─ Parse payload; resolve org by installation.id │ ├─ Dedupe by deliveryId (processed / queued / processing) │ └─ Persist GitHubWebhookDelivery (status: queued, metadata.rawBody) │ └─ after(() => processQueuedGitHubWebhookDeliveries({ deliveryId, limit: 1 })) └─ Async processing in same request lifecycle (Next.js after())

5.1 Verification

verifyGitHubWebhook in lib/github.ts computes sha256=HMAC(secret, rawBody) and compares with x-hub-signature-256 using constant-time equality. Failures return HTTP 401.

5.2 Enqueue and dedupe

enqueueGitHubWebhookDelivery uses the x-github-delivery header as deliveryId:

  • If status is processed → duplicate, not re-queued
  • If status is queued or processing → duplicate, no new row
  • Failed deliveries can be re-queued on retry with updated metadata
  • Without database or deliveryId → demo mode response, not queued

5.3 Processing and retry

processGitHubWebhookDelivery marks the delivery processing, increments attemptCount, resolves the org by payload.installation.id, routes by event type, then sets status to processed or ignored. On exception, status becomes failed with nextRetryAt computed by exponential backoff: 

retryDelayMs(attempt) = min(60_000 × 2^(attempt−1), 15 × 60_000)

processQueuedGitHubWebhookDeliveries picks deliveries where status is queued, or failed with nextRetryAt ≤ now (or null). Default batch size is 10; the webhook route processes one delivery immediately via after(). Owners/admins can trigger batch retry via POST /api/github/webhook/retry (limit 25).

6. Event Types

Event Handler Behavior
pull_request processPullRequestWebhook Ensures repository row; routes by action (see below)
pull_request_review processPullRequestReviewWebhook Maps GitHub review approved / changes_requested to Auteur approval status; creates Approval and audit/activity rows
check_run processCheckWebhook Updates PR ciStatus from check payload
check_suite processCheckWebhook Same as check_run
workflow_run processCheckWebhook Same as check_run
installation syncGitHubInstallation Full installation resync when repos are added/removed or install changes
installation_repositories syncGitHubInstallation Same as installation
Other events — Marked ignored with message "Event … is not handled yet."

6.1 Pull request actions

pullRequestSyncActions triggers full sync via syncGitHubPullRequest:

opened synchronize reopened edited ready_for_review

closed updates status only (merged / closed) without re-running the full analysis pipeline. Other actions are ignored.

If no org matches the installation ID, the delivery is marked ignored: "No organization is connected to this GitHub installation."

7. CI Updates

Check events (check_run, check_suite, workflow_run) update existing synced pull requests only — they do not import new PRs.

7.1 PR resolution

  1. Prefer PR number from checkPayload.pull_requests[0].number
  2. Else match by head_sha on the repository (most recently updated)

7.2 Status mapping

mapGitHubCiStatus converts GitHub check/workflow status to Auteur CiStatus:

GitHub Auteur
queued, in_progress, requested, waiting, pending pending
completed + success / neutral / skipped passing
completed + failure / timed_out / cancelled / action_required / startup_failure failing
Other combinations unknown

When CI resolves to passing or failing, an AgentActivity row is created (ci_passed or ci_failed). Note: PR sync initially sets ciStatus: 'unknown'; webhooks are the primary path for live CI state after sync.

8. GitHub Output

Auteur publishes back to GitHub in two layers: governance check runs during PR sync, and AI review output after job completion.

8.1 Auteur check run (lib/github.ts)

publishAuteurCheckRun creates or updates a check run named Auteur on the PR head SHA. Conclusion comes from getAuteurCheckConclusion:

Condition Conclusion
approvalStatus === 'rejected' or ciStatus === 'failing' failure
pending, testGapStatus === 'high', or riskLevel === 'critical' action_required
approved, risk_accepted, or not_required success
Otherwise neutral

Existing githubAuteurCheckRunId on the PR is used for update; 404 falls back to create. Check run ID is persisted on the PR row after live publish.

8.2 AI review output (lib/github/output.ts)

publishAiReviewGitHubOutput runs after AI review jobs when the plan includes githubComments (isFeatureAvailable(planKey, 'githubComments')). Three publish channels (all default on, configurable via settings):

  • Inline review — postPullRequestReview with COMMENT event and line-level findings
  • Managed comment — postPullRequestComment; updates existing comment via githubManagedCommentId
  • AI review check run — publishAiReviewCheckRun named Auteur AI Review

Markdown is sanitized (sanitizeGitHubMarkdownText): strips control chars, neutralizes @, and truncates long bodies. Managed comments include an "Open in Auteur" link.

8.3 Plan gating

shouldPublishGitHubCheckRun(planKey) in sync and publishAiReviewGitHubOutput both require getPlanEntitlements(planKey).features.githubComments. Without entitlement, sync still persists PR data but skips check run publish; AI output returns mode: 'blocked'.

9. Usage Metering Interaction

Each full PR sync through syncGitHubPullRequestRecord consumes one PR check against the org's plan limit, unless already recorded for the same source key in the current billing period.

9.1 Source key

getPrCheckSourceKey({ repositoryId, pullNumber, headSha })
  → "{repositoryId}:{pullNumber}:{headSha}"

9.2 canRunPrCheck

  1. Look up existing UsageRecord for metric pr_checks, current period, and source key — if found, allow (idempotent retry)
  2. Load org plan; get prCheckLimit from entitlements
  3. Compare current usage via getPrCheckUsage and canConsume(limit, used, 1)

If canRunPrCheck returns false, syncGitHubPullRequestRecord exits early without syncing — webhook and manual sync both respect this gate.

9.3 Recording usage

After successful upsert, recordPrChecks(organizationId, 1, date, sourceKey) writes the usage row. On success, repository.monthlyPrCheckUsage is incremented.

10. Demo vs Live Mode

Condition Mode Behavior
Missing GITHUB_APP_ID or GITHUB_APP_PRIVATE_KEY demo isGitHubDemoMode(); Octokit clients return null; API helpers return mock messages instead of calling GitHub
Missing GITHUB_WEBHOOK_SECRET (non-production) demo Webhook verification passes without signature check
Missing GITHUB_WEBHOOK_SECRET (production) live Verification fails with missing_secret → HTTP 401
No PostgreSQL / no deliveryId demo Webhooks acknowledged but not queued or processed
Org missing githubInstallationId demo Sync routes return demo message; no GitHub API calls
All credentials + DB + installation present live Full GitHub API, webhook queue, and output publish
Demo output is non-destructive In demo mode, postPullRequestComment, postPullRequestReview, and check run helpers return descriptive mock messages — nothing is posted to GitHub.

11. Caveats

Topic Detail
Single installation per org Only one githubInstallationId is stored; reinstall overwrites the previous link.
Open PRs only on list sync listGitHubPullRequests uses state: 'open'; closed PRs are updated via webhooks or direct single-PR sync.
CI at sync time Full PR sync sets ciStatus: 'unknown'; rely on check/workflow webhooks for accurate CI.
Usage limit skips sync When PR check quota is exhausted, sync silently returns false — no partial import.
Webhook without connected org Deliveries for unknown installations are marked ignored, not retried indefinitely.
Check run publish failures Sync succeeds even if publishAuteurCheckRun throws; failure is logged with console.warn.
Repository limit on sync New repos from installation sync are skipped when plan repository limit is reached (existing repos still update).
Private key formatting GITHUB_APP_PRIVATE_KEY must use literal \n for newlines in env; code replaces before use.
Immediate async processing after() processes one delivery per inbound webhook; sustained load depends on retry route or job cron (see jobs doc).
