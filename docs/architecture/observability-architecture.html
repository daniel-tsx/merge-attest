1. Overview

AgentGate observability is deliberately lightweight: a single module (lib/observability.ts) emits one JSON object per log line to stdout/stderr. Vercel (or any log aggregator) captures these lines. There is no in-app Sentry, PostHog, Datadog, or OpenTelemetry exporter — operators rely on platform logs plus the authenticated /api/diagnostics endpoint for dependency and queue health.

Application code │ ├─ logEvent() → console.log / warn / error (JSON line) ├─ reportError() → logEvent(level: error) + error metadata │ ▼ Vercel / hosting log drain │ ├─ Filter by area, action, release (VERCEL_GIT_COMMIT_SHA) └─ Correlate with /api/diagnostics for queue + dependency state Product analytics & error SaaS: intentionally not wired in-app

2. Structured Logging (lib/observability.ts)

2.1 logEvent()

Emits a single JSON object per call. Fields:

Field Description
timestamp ISO-8601 UTC
level debug | info | warn | error (default info)
area Domain tag (see §3)
action Stable snake_case event name for filtering
message Human-readable summary
environment NODE_ENV
release Deploy version (see §4)
metadata Flat key/value context (strings, numbers, booleans, null) 
{
  "timestamp": "2026-06-03T12:00:00.000Z",
  "level": "info",
  "area": "github",
  "action": "webhook_enqueued",
  "message": "GitHub webhook queued for processing.",
  "environment": "production",
  "release": "abc123def456",
  "metadata": { "event": "pull_request", "deliveryId": "...", "queued": true }
}

2.2 reportError()

Convenience wrapper that logs at level: error. Adds error metadata:

  • errorName, errorMessage from Error instances
  • errorStack — included in non-production only (stripped in production to reduce noise/leakage)
  • Non-Error values serialized as error: String(value)

2.3 getErrorTrackingContext()

Returns { environment, release } from runtimeContext() — a hook for future external error tracking without coupling the app to a vendor today.

4. Release Context

Every log line includes a release field from runtimeContext():

  1. VERCEL_GIT_COMMIT_SHA — set automatically on Vercel deploys (preferred)
  2. APP_VERSION — manual override
  3. NEXT_PUBLIC_APP_VERSION — client-visible fallback
  4. 'local' — development default

During incident triage, filter logs by release to correlate errors with a deploy. The operations runbook recommends confirming deploy version via these fields when investigating webhook or job failures.

5. Intentionally No Sentry / PostHog

By design The codebase contains no Sentry SDK, PostHog client, or other third-party observability packages. Product analytics and exception SaaS are deferred to keep the attack surface, bundle size, and privacy posture minimal.
Capability Current approach Future option
Exception tracking reportError() → JSON stderr; Vercel log alerts Log drain → external error tracker; or wire getErrorTrackingContext()
Product analytics None in-app PostHog or similar if privacy policy updated
Audit trail PostgreSQL AuditEvent table (compliance, not ops logs) See audit architecture
APM / traces None Vercel observability or OpenTelemetry if needed

6. Public Health — GET /api/health

Liveness-only endpoint. No authentication. Always returns { "status": "ok" } when the route handler executes.

  • Logs health_check at area: health on each request.
  • Does not probe database, GitHub, or billing — suitable for uptime monitors only.
  • Use /api/diagnostics for dependency readiness (see §7).

7. Owner/Admin Diagnostics — GET /api/diagnostics

Authenticated endpoint for workspace owners and admins only. Returns JSON combining org context, dependency checks, and recent webhook failures.

7.1 Access control

  • Requires session + database (ensureCurrentUserOrganization()).
  • 401 if unauthenticated or no DB.
  • 403 if role is not owner or admin.

7.2 Response shape

{
  "status": "ok" | "warning" | "error",
  "organization": { "id", "name", "planKey", "billingStatus", "repositoryCount", ... },
  "checks": [ { "name", "status", "message", "metadata?" } ],
  "recentWebhookFailures": [ { "deliveryId", "event", "attempts", "lastError", ... } ]
}

Top-level status is computed by summarizeDiagnostics(): any check with error → error; else any warning → warning; else ok.

7.3 Checks from lib/diagnostics.ts

Check name What it validates
database DATABASE_URL configured + SELECT 1 succeeds
github GitHub App credentials configured (githubConfigured())
lemon_squeezy Billing mode live vs demo/warning
job_runner JOB_RUNNER_SECRET present
email Transactional email mode live vs demo
jobs Failed GitHub webhook delivery count (org-agnostic queue stats)
ai_review_jobs Queued/active/blocked/failed/stale AI review jobs
retention Stale processed webhook deliveries (>30d) or audit export records (>30d)

getJobRunnerDiagnostic() is also exported for reuse and accepts an optional env override (used in tests).

8. What Gets Logged on Webhook Failures

8.1 GitHub — ingress (/api/github/webhook)

Failure Log HTTP
Invalid/missing HMAC logEvent warn · webhook_verification_failed · metadata: reason 401
Invalid JSON body No structured log (SyntaxError caught) 400
Enqueue/processing exception reportError · webhook_processing_failed · metadata: event, deliveryId 500
Success enqueue logEvent info · webhook_enqueued 202 / 200

8.2 GitHub — async worker (/api/jobs/github-webhooks)

When queued delivery processing throws, reportError logs queued_github_webhook_failed with deliveryId, event, and attemptCount. Delivery row updated with lastError — surfaced in /api/diagnostics recentWebhookFailures (org-scoped, last 5).

8.3 Lemon Squeezy (/api/lemon-squeezy/webhook)

Failure Log HTTP
Invalid signature reportError · lemon_squeezy_webhook_failed 401
Bad payload Same action; message from thrown Error 400
Processing error reportError in processor (lib/lemon-squeezy-webhooks.ts) 500
Success logEvent · lemon_squeezy_webhook_processed 200

9. Operational Triage Workflow

From docs/operations/OPERATIONS_RUNBOOK.md:

  1. Alert on GET /api/health non-200 for liveness.
  2. Owner/admin checks GET /api/diagnostics for dependency warnings.
  3. Filter platform logs by area + action + release.
  4. Inspect recentWebhookFailures or GitHub settings UI for delivery errors.
  5. Trigger job endpoints manually: /api/jobs/github-webhooks, /api/jobs/pr-reviews, /api/jobs/retention.
Logs are not durable product data Platform log retention depends on Vercel/plan settings. Compliance evidence lives in AuditEvent rows, not stdout JSON lines.
